# Translations (i18n)

The desktop app's screens are in English and Hindi (हिन्दी) (STEPS 8.8). The layer is ours, under 200 lines in `apps/desktop/src/lib/i18n.ts`, with no library.

## How it works

- **The English sentence is the key.** `t('Pause')` shows `रोकें` in Hindi. A string with no translation shows in English, so nothing ever goes blank, and tests that look for English text keep working.
- **Catalogues** are plain objects, English → translation: `src/locales/hi.ts`. English has none.
- **Choosing the language:** Settings → Look and feel → Language: System, English or हिन्दी. System follows the computer (`navigator.languages`: the first of Hindi or English it lists). The choice is a per-window UI preference, kept in local storage and read before the first paint. `<html lang>` follows it.
- **The demo** (a plain browser, Playwright) starts in English whatever the machine's language, so tests never depend on it. `?lang=hi` (or `?lang=en`) picks one for that page load; a choice made in Settings is kept as in the app.
- **Re-rendering:** the language lives in a tiny zustand store (`useLang`). `App` subscribes with `useLocale()`, so the whole tree re-renders on a change and every `t()` reads the new language. Nothing is memoised across a language change; keep it that way (a `useMemo` that builds text needs the locale in its dependencies).
- **Numbers, sizes, speeds, dates and times** go through `Intl` with `intlLocale()`: `hi-IN` for Hindi (Western digits, Indian grouping such as 12,34,567), and the computer's English (`en-GB`, `en-IN`…) for English. Use the helpers in `lib/format.ts` (`bytes`, `rateText`, `num`, `clockTime`, `when`, `startsAt`, `readyBy`, `eta`) rather than `toLocaleString()` with no locale.
- **Text from the core** (errors and hints, why a download failed, notes on a download, feed and watch-folder results, Nearby and Send problems) is translated where it's shown: see [Text from the core](#text-from-the-core). Network names from the OS and file names are shown as sent.

## Adding a string

```tsx
import { t, tn, tr, mark } from '../lib/i18n'

<button>{t('Pause')}</button>
<button aria-label={t('Remove {name}', { name: job.name })}>…</button>
<p>{tn(files, '{n} file', '{n} files')}</p>
<p>{tr('Saved to {folder}.', { folder: <code>{dir}</code> })}</p>
const WORDS = { sleep: mark('Your computer goes to sleep') } // … t(WORDS[action])
```

1. Wrap it: `t()` for text, `tn(n, one, other)` for a count (`{n}` is the count), `tr()` when elements sit inside the sentence, `mark()` in a table or constant that `t()` translates where it's shown.
2. Pass **whole sentences** with `{names}`, never pieces glued together: Hindi puts the verb last, so `t('Starts') + ' ' + time` can't be translated, and `t('Starts {when}', { when })` can.
3. Add the Hindi to `src/locales/hi.ts` under its area.
4. Run `node scripts/i18n-check.ts` in `apps/desktop` (the UI tests run it too). It fails on a string with no Hindi, `{names}` that differ, English left in JSX (text, `aria-label`, `title`, `placeholder`, `alt`, `label`) outside `t()`, a sentence built from pieces, `t()` at module level (it would keep the first language), and Hindi left over after its English changed. `--loose` also lists other strings that look like English sentences, to review by eye.

Text that is never translated: brand and product names (Fuselane, Fuse Send, LocalSend, AriaNg, aria2, yt-dlp, ffmpeg, BitTorrent, GitHub), file names, links, folders, keyboard keys, units (KB, MB, GB, MB/s, Mbps), standards (Wi-Fi, Ethernet, VPN, USB, DNS, SHA-256, RSS, Metalink, QR) and code. Mark elements that show a name or a file with `translate="no"`, so browser translators leave them alone too. If a line really must stay English, add `i18n-ignore` in a comment on it or the line above.

Ids must never come from translated text (`id={slug(t(title))}` gives every Hindi heading the same id): pass a fixed id.

## Text from the core

The Rust core writes English (the CLI and logs use the same words), and the app translates what it shows. The table is `src/locales/hi-backend.ts`, English → Hindi, and `lib/backendMatch.ts` does the matching with no library:

- **A plain sentence** is looked up as is: `'Paste a link to download.'`.
- **A sentence with parts that change** is a template: `"{network}'s proxy at {at} didn't answer in time."`. It's turned into an anchored pattern (`^(.+?)'s proxy at (.+?) didn't answer in time\.$`) and must match the whole text; the parts it captures go into the Hindi. Templates with more fixed text are tried first, so `Starts at {when} tomorrow.` wins over `Starts at {when}.`.
- **A part that is itself a sentence from the core** is translated too, when its name says so: `why`, `e`, `last`, `reason`, `problem`, `next`, `what`, `todo` or `m` (`Every network failed. Last problem: {last}`). Any other name (a file, a network, an address, a number) is kept exactly as sent. A part may be missing its full stop (`Not added: {why}.`) or carry one: both are tried.
- **Text made of several sentences** (a message and its hint, `{what} {todo}`) is split where a sentence ends and each run is translated; sentences the table doesn't know stay in English.
- **Anything else is shown as sent**, in English. Nothing breaks when the core adds a sentence the table doesn't know yet.

Where it's applied: `toUiError()` (every error a command returns, so toasts, dialogs and form errors), and with `tb()` where polled text is shown: a download's failure and mirror notes, network notes, a torrent's or a send's error, Nearby problems and sync notes, feed problems and recent notes, the watch folder's problem and recent notes, the remote control's problem, the network check's phase and problems, the schedule's next change, a proxy check's result and skipped links in a batch. `tb()` runs at render, so a language change applies at once (an error already in a toast keeps its language until it closes).

**Adding one:** copy the sentence exactly as the Rust writes it (`git grep` the message), turn each `{}` / `{e}` / `{x:?}` into a `{name}` (one of the names above when the part is a sentence from the core), and add the Hindi with the same names. If the demo backend (`src/lib/demo*.ts`) sends it, `scripts/i18n-check.ts` already wants it. The check also fails on an entry with no Hindi, different `{names}`, a dash, no Devanagari, a key written twice, or a template that a wider one takes over (each template, filled with sample parts, must come out as its own Hindi).

**Left in English** (on purpose or not yet):

- Details from the system or a library inside a message: OS errors (`Permission denied (os error 13)`), TLS and connection errors, the disk failure kind in `Saving failed (…)`, yt-dlp's own words, the last network error inside `Couldn't reach the server…`.
- The torrent path checks' details (`"x" has a name Windows can't store`), and rare messages not in the table yet: new sentences show in English until someone adds them.
- What Fuselane shows outside the window: system notifications ("Download finished"), the tray's tooltip, the "when done" countdown notice and the native file dialogs' titles.
- Names the core makes up: a group's default name (`3 files from example.com`), the placeholder name of a receive (`Receiving…`), and the video quality labels (`Audio (MP3)`).
- Text for other programs and devices: the aria2 remote control's JSON-RPC replies (AriaNg shows them), the browser extension's API errors, the phone page served to a phone's browser, the network check's HTML report, and the CLI.

## Adding a language

1. Copy `src/locales/hi.ts` to `src/locales/<code>.ts`, and `hi-backend.ts` to `<code>-backend.ts`, and translate the values (keep the keys and the `{names}`).
2. In `lib/i18n.ts`: add the code to `Locale`, the catalogues to `CATALOGUES` and `BACKEND`, its Intl tag to `intlLocale()`, and its base code to `systemLocale()`.
3. Add it to the Language setting (`LANGUAGES` in `SettingsView.tsx`), written in its own language.
4. Teach `scripts/i18n-check.ts` to read the new catalogue, and add a Playwright test like `tests/i18n.spec.ts`.
5. Check the screens at 375 px and 1440 px, light and dark: longer words wrap differently.

## Hindi style

Everyday Hindi as Indian apps use it (Google, PhonePe, WhatsApp): short, polite and plain, in Devanagari.

- Address people as आप. Buttons are polite requests ending in -ें / -एं: खोलें, हटाएं, भेजें, चुनें, जोड़ें. Write the nasal with the dot (anusvara: हटाएं, जांच, यहां, अपने आप), not the moon (चंद्रबिंदु).
- Use the English tech words people actually say, in Devanagari: डाउनलोड, अपलोड, नेटवर्क, फ़ाइल, फ़ोल्डर, लिंक, टोरेंट, सेटिंग्स, स्पीड, डिवाइस, अपडेट, शेड्यूल. Write the nukta in loanwords (फ़ाइल, फ़ोन, फ़ीड, ज़्यादा).
- Western digits (1, 2, 3), as `hi-IN` writes them. End sentences with ।, keep … and ?. No dashes (— or –): use a comma or a colon.
- Keep labels short: tabs, nav and buttons should fit on one line at 375 px.
